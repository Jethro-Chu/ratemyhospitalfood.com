## 2. Confirmed findings and prepared fixes

| Finding | Evidence | Local fix |
| --- | --- | --- |
| High: public schema administration | `/seed` is an unauthenticated GET route in the deployed Git source and build. It creates tables/extensions/indexes, alters columns, and returns database error messages. It was deliberately not invoked on the live site. | Remove the web route. Move required changes to `migrations/20261021_security.sql`. Remove schema-repair DDL from the public reaction handler. Local `/seed` returns 404. |
| High: unsafe public image upload | Deployed handler trusts client `file.type` and uses the user filename's extension; there are no request quotas. Client-side compression can be bypassed. | Bound actual multipart bytes before parsing, cap file size/pixel count, decode only JPEG/PNG/WebP, reject malformed/animated input, resize/re-encode JPEG without metadata, assign a cryptographic random `.jpg` path, and apply shared quotas before decoding. No user filename is retained. |
| High: public write abuse and alternate bypasses | Reviews, hospital-creation Server Actions, and reactions lack shared limits. Legacy review action bypasses API validation. Reactions accept unlimited positive deltas and can decrement other visitors' counts. | Shared atomic PostgreSQL per-client/global hourly budgets for reviews, uploads, hospital creation, and reactions. Use common review validation in both API and Server Action. Track signed-browser reaction ownership in an atomic ledger: repeated +1 is idempotent; -1 removes only that browser's row. Missing DB/security configuration fails closed. |
| Invalid/untrusted review input | `parseInt('5junk')` is accepted; strings are unbounded; arbitrary `imageUrl` values can be stored. The configured database lacks rating/text CHECK constraints. SQL parameters already prevent ordinary SQL injection. | Strict UUID, integer 1-5 rating, name/comment bounds; new photos require an HttpOnly signed receipt from the upload handler and the exact known Blob host/path. Add database constraints for new writes without deleting legacy records. Limit image optimization to the observed store's photo path. |
| Overprivileged configured DB connection | Read-only catalog inspection identifies `neondb_owner` with role/database creation and RLS bypass. Tables are owner-controlled. This is confirmed for the existing local credential; production use of that same role is not independently verified. | Prepare a restricted `food_runtime` group role: public-table SELECT, narrow hospital/review INSERT columns, reaction-counter UPDATE only, and limited budget/ledger access. No schema ownership, private-table grants, table deletion, or review-content UPDATE. Production migration and credential switchover remain pending. |
| Vulnerable dependencies | OSV found 72 package/advisory matches in the deployed lockfile. The app has Server Actions, relevant to the Next App Router DoS advisory; some other advisories require conditions not demonstrated here. | Upgrade Next and eslint-config-next to **15.5.28**, sharp to **0.35.5**, and patch affected compatible transitives with exact overrides. Retain React 18 and the existing UI/game code. |
| Missing browser hardening | Live HTML lacked nosniff, frame protection, CSP, and Referrer-Policy; Next version header was exposed. HSTS was already present. | Add focused CSP/base/object/frame/form restrictions, `nosniff`, `SAMEORIGIN`, and Referrer-Policy; disable powered-by header. |

The Next upgrade addresses version matches including [Server Action DoS](https://github.com/vercel/next.js/security/advisories/GHSA-m99w-x7hq-7vfj) and [AVIF image processing](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4). No exploit was run against the live service.

Other review results:

- No credential patterns were found in tracked files, reachable historical text blobs up to 2 MB, or the nine JavaScript assets referenced by the live homepage. Existing local database credentials were read only in-process and never printed/copied into the new checkout. Vercel and Blob environment secrets could not be inspected.
- Database catalog inspection showed only `hospitals` and `reviews` in public, no RLS policies, and no non-owner table grants. **RLS being disabled is not itself proof of browser data exposure:** this app uses server-side SQL, not a browser PostgREST/Supabase Data API. No anonymous direct-database access was established. Catalog-only production reads were used; attack tests ran in isolated PostgreSQL.
- SQL remains parameterized. A synthetic SQL/XSS string was stored as ordinary text in the test DB; the hospitals table remained intact. Review components render comment/name strings as React text. No confirmed application XSS or SQL injection was found.
- Mutation handlers check browser Origin/Sec-Fetch-Site. Signed actor/photo cookies use HttpOnly, Secure in production, and SameSite=Strict. There are no private user accounts; reviews and hospitals intentionally accept anonymous contributions. Origin checks do not authenticate a person.
- Client-IP handling accepts Cloudflare's visitor header only on the custom domains and only behind a Vercel-observed Cloudflare network peer. Direct Vercel aliases cannot supply a trusted CF visitor header. Official [Cloudflare ranges](https://www.cloudflare.com/ips/) and [header behavior](https://developers.cloudflare.com/fundamentals/reference/http-headers/) informed this code. Actual proxy/Worker configuration still needs verification in a preview.

## 3. Verification

- `npm run build`: passes with Next 15.5.28 on local Node 22.22.2. The build intentionally has no production DB secrets: database-backed pages use their existing fallback/empty states. This does not verify the live DB content end-to-end. An existing unrelated game hook warning remains.
- `npm run verify:security`: **45 assertions pass** using an in-memory real PostgreSQL engine (PGlite) and fake Blob provider. No production URL or `.env` is loaded.
- Tests cover runtime-role rejection of private-table reads, schema creation/ALTER, review text UPDATE, and DELETE; database rating constraints; invalid ratings/UUIDs/text; alternate-action validation; cross-origin rejection; streamed body bounds; fake MIME files; valid image re-encoding; signed upload receipts; idempotent reactions; ownership of reaction removal; quotas; and proxy-header spoofing.
- Local HTTP smoke: homepage 200, `/seed` 404, expected security headers present. Browser smoke confirms the existing homepage structure/navigation renders. The application forms/storage boundary is covered by the isolated route/SQL/Blob tests; a real hosted Blob upload was not performed.
- OSV checked all **541** versioned entries in the prepared lockfile. Only `braces` 3.0.3 / `GHSA-vfj7-8cjw-p6xm` remains, with no published upstream fix. It is pulled in by build/tooling glob processing; no public input path to this parser was found. Standard npm audit endpoints timed out, so the complete OSV batch result is recorded in `audit/dependency-audit.json`.
- `git diff --check` passes. Original Documents checkout and its work remain untouched. No visual components or game logic were edited.

## 4. Required release changes, credentials, and access

1. Review the local code and **once-only** migration `migrations/20261021_security.sql`. Test it first on an isolated hosted database/branch. It adds budget/reaction tables and constraints, revokes PUBLIC grants, and creates the restricted group role. It does not delete reviews. Existing reaction totals are retained as a baseline; old anonymous reactions cannot be attributed retroactively.
2. With a database administrator, create a separate LOGIN and grant it `food_runtime`. Use that login's pooled connection as production `POSTGRES_URL`. Keep the owner URL out of application runtime. After switchover, rotate the old owner password and remove obsolete owner credential aliases from runtime/build environments. This is a privilege-reduction rollout, not evidence the password leaked. No credential was rotated here.
3. Generate a random server-only `APP_SECURITY_SECRET` (at least 32 bytes). Configure the exact `REVIEW_PHOTO_HOST` if migrating stores and confirm the Blob write token is scoped to that store. No signing secret was committed. Rotating it later invalidates actor/photo cookies.
4. Deploy a reviewed preview with isolated DB/Blob storage. Verify a real photo -> upload receipt -> review -> rendered image flow, Server Actions, signed cookies, reaction undo, Cloudflare visitor-IP behavior, and quotas. The application intentionally returns 503 for submissions until the required tables/configuration are present.
5. Arrange periodic cleanup of expired `security_rate_limits` rows through an admin maintenance job; the migration contains the query. Consider CAPTCHA/moderation if actual abuse exceeds the anonymous quotas. These limits are not Sybil-proof identity verification.
6. Vercel environment metadata was denied with 403; existing local CLI authorization was invalid. The Neon connector was not connected, although existing DB credentials allowed catalog reads. Access is needed to Vercel environment settings, the relevant Neon management account, Blob settings, and Cloudflare zone/Worker/WAF configuration to finish the hosting review. Never paste their tokens in chat.
7. Only after approval, deploy/migrate and verify production aliases, `/seed` 404, header delivery through Cloudflare, valid submissions and unauthorized denials. Production traffic was not modified by this task.

## 5. Unverified/residual scope

Production fixes are **not deployed or verified**. The current production DB credential/role and exact deployment-to-Neon linkage, Cloudflare rules/Workers/cache behavior, Vercel WAF, Blob token scope, existing uploaded-file contents, managed-service internals, full production logs and compromise history remain unverified. No claim is made that old public photos were scanned or cleaned. Photo metadata is stripped on new uploads only. The CSP is intentionally focused and does not constrain every script source. Anonymous moderation, orphan-upload lifecycle, coordinated fraud, and provider spending alerts remain operational work. This audit does not establish that the website is completely secure.
